# Kicks mobile

React Native with Expo SDK 55, Expo Router and NativeWind (Tailwind utilities). The approved cream/orange campaign, locally bundled Anton and Manrope fonts, and campaign photography guide both native and web screens. Native Shop now includes the hero photograph selector, collections, editorial feature, category/search/price controls, FAQ and orange footer. A native field-guide route links back into the same catalogue categories. Radix/shadcn DOM components cannot run in React Native; small accessible native controls reuse the same design conventions instead.

## Connection configuration

Run mobile commands from the repository’s `mobile/` directory.

Enter connection values yourself in `mobile/public-config.json`. This local file is ignored by Git and must not be inspected, printed or included in agent reports. For another checkout, copy `public-config.example.json` to that filename and replace placeholders locally.

- `siteUrl`: `https://kicks-topaz-eight.vercel.app`
- `supabaseUrl`: the SAME Supabase project URL used by the website.
- `supabasePublishableKey`: that project's PUBLIC publishable key.

Never put Paystack secrets, MailerSend tokens or Supabase service-role credentials in the mobile app. Client connection values are consumed by the app build; server credentials stay on the existing server. No `.env` file is required or inspected.

Native and web clients share `shared/commerce-api.js`, `shared/cart-sync.js` and `shared/guest-cart.js`, `shared/catalog.js` and shared shopping/field-guide content. Catalog, profiles, carts and orders use the existing Supabase REST endpoints with customer RLS. Checkout, verification and emails use the existing `/api/commerce` endpoint. No second account database or duplicate checkout server is introduced.

## Enable Google login and live cart updates

In the EXISTING Supabase project, add `com.kicks.shop://auth/callback` to Authentication → URL Configuration → Redirect URLs. Keep the existing website redirect and Google configuration. Mobile OAuth uses the system browser and PKCE, then stores its own session; signing into the same Google account resolves to the same Supabase user.

For an existing store with the base migrations already applied, run `outputs/supabase-upgrade.sql` in the Supabase SQL Editor. It combines the incremental private-cart migration and four additional products. It creates a private per-customer broadcast policy and a trigger for inserts, updates and deletes. Do not rerun previously applied schema migrations. Realtime notifications contain no cart rows; each client reloads its own cart through RLS. Joining, reconnecting and foregrounding refresh missed changes. Guest carts stay local until sign-in. Two devices must sign into the same account for cross-device sync.

Deploy the website changes before live testing, so the browser also subscribes to cart broadcasts. A GitHub push does not apply Supabase migrations; run the incremental SQL separately.

## Physical iPhone setup

1. Connect the unlocked iPhone by USB. Tap **Trust This Computer** and enter the phone passcode on the phone.
2. Open Xcode → Window → Devices and Simulators. Select the phone and allow preparation to finish. Xcode → Settings → Accounts must have an Apple ID configured for signing; enter credentials yourself.
3. On the phone, enable Settings → Privacy & Security → Developer Mode when available. Restart and confirm when prompted.
4. Use a development build, since Expo Go cannot validate this app's custom OAuth callback. Run `npm run ios` from `mobile/`, select the physical iPhone and select your signing team when asked. Native projects are generated by Expo; do not hand-edit generated files. If command-line installation fails, follow the Xcode diagnostic before retrying.
5. Keep the Mac and phone on the same Wi-Fi for the Metro development server. Run `npm start -- --dev-client` if Metro is not already running.

Expo SDK 55 was selected because the detected Xcode 26.3 meets its documented minimum; SDK 57 needs Xcode 26.4+. EAS offers an alternative signed cloud development build: `npx eas-cli@latest build --platform ios --profile development`. This needs your Expo/Apple account configuration and device registration; no cloud build or account access is performed automatically.

The `withSwiftUIModule` Expo plugin declares React Native's RCTSwiftUI pod with modular headers. This generates the public module map required by the Swift compiler when using static CocoaPods libraries. Keep this configuration when regenerating the native iOS project.

Android uses the same source. Install Android Studio/SDK and connect an Android phone with USB debugging, then run `npm run android`; alternatively create an EAS development build with `--platform android`.

## Acceptance test on a real phone

Record the date, app build, actual device/OS, and website deployment before marking these complete. Do not record customer data, tokens or keys.

1. Website and phone: sign in with the same Google account. Confirm the account and existing order history match.
2. Website: add a specific pair and EU size while signed in. Phone: keep Bag open and confirm it appears without manual refresh. Record measured delay; no latency is claimed from local tests.
3. Website: increase quantity, decrease quantity and remove the pair. Confirm each change on the phone. Repeat phone → website.
4. Background the app, change the bag on the website, foreground it, and confirm recovery. Repeat after disconnecting/reconnecting network access.
5. Force-close and reopen the app. Confirm the account session and saved cart restore. Sign out of the app and confirm it no longer displays that account's cart.
6. Sign in with a different account and confirm it cannot read the first account's cart or orders.
7. Complete a labelled simulated payment when the server enables it. Confirm a persisted demo order, cart clearing on both devices, and the actual receipt delivery separately. Never treat local tests as provider delivery proof.

Paystack opens the existing hosted payment screen in the system browser. Its existing HTTPS website callback performs server verification; return to the app and check Account/orders afterward. The mobile app does not claim successful payment from a browser close or a redirect.
